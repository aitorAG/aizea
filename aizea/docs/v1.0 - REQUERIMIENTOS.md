# v1.0 — Documento de toma de requerimientos

> **Fecha**: 2026-07-27
> **Origen**: Sesión de revisión del proyecto con el cliente.
> **Naturaleza**: Requerimientos en bruto, en la voz del cliente. Fija el
> **qué se pide**. El *cómo* se aborda en el documento de diseño; el *cuándo/en
> qué orden* en el plan de implementación.

Esta es la primera toma de requerimientos formal (hito v1.0). Recoge lo que el
cliente ha identificado como necesario tras revisar el producto. Cinco frentes
más un parámetro transversal de granularidad.

---

## R1 — Los elementos visuales de los materiales deben tener diapositiva propia

Los materiales que se suben a veces contienen **fotografías, gráficos, fórmulas
u otros elementos visuales**. El cliente pide que:

- **R1.1** Cada elemento visual tenga **su propia diapositiva**.
- **R1.2** El visual aparezca en esa diapositiva **tal y como aparece en el
  material original**. *(El cliente marca esto como crucial.)*
- **R1.3** Decisión de fidelidad acordada en la sesión: **mixto** — las
  **fotografías y gráficos** se muestran como **recorte real** de la imagen del
  original; las **fórmulas** se **re-renderizan** (nítidas y escalables) en
  lugar de recortarse.
- **R1.4** Colocación acordada: **una diapositiva por visual**, situada
  **justo después de la diapositiva del concepto/hoja al que pertenece** ese
  visual.

## R2 — Renderizado correcto de la diapositiva y export a PDF de dos páginas

El renderizado actual de las diapositivas no sale correctamente. El cliente
define el objetivo:

- **R2.1** La diapositiva se renderiza **a pantalla completa en formato
  apaisado**, como un **A4 horizontal**.
- **R2.2** Proporción en pantalla acordada: **A4 apaisado (√2:1)**, de modo que
  **lo que se ve en pantalla es exactamente lo que se exporta** (coherencia
  total pantalla ↔ PDF).
- **R2.3** El export a PDF produce, **por cada diapositiva, dos páginas**:
  - **Página 1**: la **diapositiva** en **A4 horizontal**.
  - **Página 2**: el **contenido de esa diapositiva** — narrativa, ejercicios,
    explicación y demás — en **A4 vertical**.

## R3 — El orden de las diapositivas debe seguir la estructura del árbol

El orden actual de las diapositivas no es coherente. El cliente pide:

- **R3.1** Las diapositivas deben seguir **la misma estructura que el árbol** y
  que la lista de diapositivas, porque representan el contenido de los
  materiales.
- **R3.2** El recorrido es **de arriba abajo** en el árbol (no de izquierda a
  derecha): el orden lineal de las diapositivas corresponde a recorrer el árbol
  **de arriba abajo** respetando su jerarquía.

## R4 — Chatbot-agente para editar el árbol conversando

El cliente plantea la posibilidad de, en la vista de generación del árbol,
tener un **chat** que permita a un **agente/chatbot** interactuar con el árbol y
con el usuario para ir haciendo las modificaciones que el usuario pida:

- **R4.1** El agente entiende **todo el árbol** y decide qué modificaciones
  hacer a partir de lo que el usuario le va diciendo (conversación).
- **R4.2** El agente puede ejecutar **acciones sobre el árbol**: **crear hoja**,
  **eliminar hoja**, **fusionar hojas** (el cliente menciona una especie de
  "plan graph" / agente composicional que decide y ejecuta acciones).
- **R4.3** Las modificaciones que el agente va haciendo a partir de la
  conversación se **reflejan en tiempo real** en el gráfico/visual de la página
  web, **sin que el usuario tenga que recargar** la página.
- **R4.4** Alcance acordado: se aborda **en esta misma ronda**, junto al resto.
- **R4.5** Efecto sobre diapositivas ya generadas acordado: al crear/eliminar/
  fusionar hojas, las **diapositivas de las ramas afectadas se regeneran
  automáticamente**.

## R5 — Elección de cantidad orientativa de diapositivas en la primera generación

Al generar el árbol por primera vez, el usuario debe poder indicar cuántas
diapositivas quiere, de forma **orientativa** (no un límite duro):

- **R5.1** Mecanismo acordado en la sesión: un **slider con un contador de
  diapositivas objetivo, de 0 a 300**.
- **R5.2** Este parámetro se usa como **estimación del nivel de granularidad /
  detalle** deseado, no como un tope rígido. El sistema lo toma como una guía
  aproximada (un plan/estimación).
- **R5.3** El valor debe estar **disponible para el chatbot-agente** (R4) para
  que lo tenga en cuenta al proponer o ejecutar modificaciones sobre el árbol.
- **R5.4** Origen conceptual (los tres niveles orientativos que motivaron el
  slider): ~20 (≈15–30), ~50, ~200 (≈50–300). El slider generaliza esa idea a
  un rango continuo 0–300.

## Parámetros transversales / decisiones de la sesión

| Tema | Decisión |
|---|---|
| Fidelidad visual (R1) | Mixto: fotos/gráficos = recorte real; fórmulas = re-render KaTeX |
| Colocación de visuales (R1) | Una diapositiva por visual, tras el concepto al que pertenece |
| Proporción diapositiva (R2) | A4 apaisado (√2:1), idéntico pantalla y PDF |
| PDF por diapositiva (R2) | 2 páginas: p1 diapositiva (apaisado) + p2 contenido (vertical) |
| Orden de diapositivas (R3) | DFS del árbol, de arriba abajo |
| Alcance del chatbot (R4) | Incluido en esta ronda |
| Edición de árbol ↔ diapositivas (R4) | Regeneración automática de las ramas afectadas |
| Cantidad de diapositivas (R5) | Slider 0–300 como estimación de granularidad; visible para el agente |

---

## Fuera de alcance / a confirmar en diseño

- Formato exacto del "plan graph" del agente (R4.2): se detallará en diseño como
  un conjunto de herramientas (tools) que el agente invoca; el término del
  cliente se interpreta como agente con function-calling sobre operaciones de
  árbol.
- Estrategia de regeneración automática (R4.5): alcance de "rama afectada" y
  cómo se dispara/represa se concretará en diseño.
- Transporte de tiempo real (R4.3): mecanismo concreto (streaming/SSE/estado
  cliente optimista) se decide en diseño según la infraestructura existente.
