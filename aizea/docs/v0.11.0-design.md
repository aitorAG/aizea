## D1 — Expansión incremental del árbol (R1)

### Contexto arquitectónico
- Bounded context: **Tree** (dominio conceptual del curso).
- La lógica de servicio (`TreeService.expandTreeDepth` / `expandSelectedNodesDepth`) **ya es aditiva** en BD (no borra nada). El problema es doble y vive en el **cliente**:
  1. `tree-client.tsx:641` hace `setNodes(result.nodes)` donde `result.nodes` son SOLO los hijos nuevos → borra el árbol de la vista.
  2. La selección (`selectedNodeIds`) vive dentro de `TreeViewer` y no llega al padre salvo al pulsar "Generar diapositivas" → "Bajar nivel" siempre ve `selectedIds` vacío.

### Cambios

**1. Servicio — unificar y devolver el árbol completo** (`lib/application/TreeService.ts`)
- Nuevo método privado `expandLeaves(courseId, leaves: TopicNodeRow[])` que contiene el bucle LLM + `createMany` + flip `isLeaf` (extraído del código duplicado actual).
- `expandTreeDepth(courseId)`:
  - Carga todas las hojas (`isLeaf: true`).
  - Calcula `maxDepth` y filtra **solo las hojas del nivel más profundo** (R1.2). *Decisión:* expandir el nivel más granular, no todas las hojas de cualquier profundidad — coincide con "las hojas de las hojas".
  - Elimina el aborto duro `maxDepth >= 3` como bloqueo global; en su lugar se usa un límite de profundidad razonable configurable por constante (`MAX_TREE_DEPTH = 6`) y, si una hoja ya está en el límite, simplemente se omite (no aborta toda la operación).
  - Llama `expandLeaves`, luego `recalculateTreeNumbering(courseId)` (R1.5).
  - Devuelve **el árbol completo** (`getCourseTree`), no solo los nuevos nodos.
- `expandSelectedNodesDepth(courseId, ids)`:
  - Filtra las hojas por `id ∈ ids && isLeaf`.
  - Mismo `expandLeaves` + `recalculateTreeNumbering`.
  - Devuelve **el árbol completo**.
- Fallback anti-clonado (R1.6): si `proposeSubcontents` devuelve `[]`, la hoja **se deja intacta** (no se crea un hijo clon). Solo se expanden hojas con ≥2 subcontenidos propuestos.

**Tipo de retorno unificado:**
```ts
{ ok: true; nodes: TopicNode[]; courseId: string; addedCount: number } | { ok: false; error: string }
```
donde `nodes` es **siempre el árbol completo actualizado**.

**2. Acciones** (`lib/actions/tree.ts`)
- Sin cambios de firma; siguen delegando. Aseguran `revalidatePath`.

**3. TreeViewer — exponer selección** (`components/TreeViewer/TreeViewer.tsx`)
- Nueva prop opcional `onSelectionChange?: (ids: string[]) => void`.
- `useEffect([selectedNodeIds])` que emite `Array.from(selectedNodeIds)` al padre. Se evita bucle usando el patrón de comparación por tamaño/orden ya presente en el archivo.

**4. tree-client — estado de selección vivo + merge** (`app/courses/[id]/tree/tree-client.tsx`)
- Pasar `onSelectionChange={setSelectedIds}` a ambos `<TreeViewer>`.
- `handleExpandDepth`: tras recibir `result.nodes` (árbol completo) hacer `setNodes(result.nodes)` — ahora correcto porque el servicio devuelve el árbol entero. Se conserva `router.refresh()` como sincronización secundaria.
- Mantener el toast de "N nuevos nodos".

### Descartado
- Sistema de undo/histórico: fuera de alcance de esta iteración; la garantía de no-pérdida se logra siendo aditivo. Se documenta como mejora futura.

## D3 — Generación completa contenido + HTML (R3)

### Decisión de diseño
El estado "generada" debe reflejar la realidad. Hoy `hasContent` se deriva solo de la cuenta de cajas. Se cambia a un criterio que distingue tipo de diapositiva:

- **Concepto** (`kind === "concept"`): generada ⇔ tiene cajas **y** `htmlDesign` no vacío.
- **Figura** (`kind === "figure"`): generada ⇔ tiene `htmlDesign` (sin exigir cajas).

### Cambios

**1. Señal derivada en servidor** (`app/courses/[id]/slides/page.tsx`)
- `page.tsx` ya selecciona `htmlDesign` y `kind` (verificar `kind` en el select; añadirlo si falta).
- Calcular por diapositiva:
  ```ts
  const hasBoxes = (countMap.get(s.id) ?? 0) > 0;
  const hasHtml = !!s.htmlDesign && s.htmlDesign.trim().length > 0;
  const isFullyGenerated = s.kind === "figure" ? hasHtml : (hasBoxes && hasHtml);
  ```
- Exponer en `SlideSummary`: `hasContent` (cajas) y nuevo `hasHtml`, más `isFullyGenerated` (o derivarlo en el cliente). *Decisión:* exponer `hasContent` y `hasHtml` por separado y derivar el estado visual en `SlidesHierarchy`, para poder pintar el estado intermedio (R3.3).

**2. Estado visual** (`components/slides/SlidesHierarchy.tsx`)
- `SlideSummary`: añadir `hasHtml?: boolean`.
- Cambiar la condición `isGenerated` (línea ~467):
  ```ts
  const isFully = node.slide.kind === "figure"
    ? node.slide.hasHtml
    : (node.slide.hasContent && node.slide.hasHtml);
  const isPartial = node.slide.hasContent && !node.slide.hasHtml && node.slide.kind !== "figure";
  ```
- Pintar tres estados: **generada** (verde, `isFully`), **parcial** (ámbar, "contenido, falta diseño", `isPartial`), **fallida** (rojo, ya existe vía `failedIds`).

**3. Semilla del store cliente** (`slides-client.tsx:78-80`)
- `generatedIds` inicial se siembra solo con diapositivas **plenamente** generadas (`isFully`), no con `hasContent`.

**4. Generación individual full** (`slides-client.tsx` `handleGenerateSingle`)
- Cambiar para encolar `phases: ["content","html"]` a través del `SlideGenerationQueue` (misma ruta que "Generar todo"), en lugar de solo `generateSlideContent`. Así R3.4 queda cubierto y unifica el camino de generación.

**5. Verificación del fallo HTML**
- La cola ya marca fallida la fase HTML. Se asegura que el resumen de batch propague `summary.failed` al toast final (mensaje claro cuando N diapositivas fallaron el diseño).

## D4 — Slide-generation en la pestaña Jobs (R4)

### Decisión arquitectónica
Reusar la infraestructura `ProcessingJob` existente (sin cambio de esquema; `type` es String libre y las etiquetas UI para `slide-generation` ya existen). Se escribe la fila **desde una server action nueva** que envuelve el ciclo de vida, invocada por el cliente al iniciar/progresar/terminar el batch.

*Alternativa descartada:* meter slides en `PrismaJobQueue`/`PipelineWorker` — están cableados a `pipeline-run` + `runCourse`; añadir un segundo tipo introduciría acoplamiento. Escribir filas directamente vía `container.processingJobs` es más limpio (composición sobre herencia).

### Cambios

**1. Nueva acción de ciclo de vida** (`lib/actions/slide-jobs.ts`, nuevo archivo `"use server"`)
```ts
export async function startSlideJobAction(courseId, total): Promise<{ jobId: string }>
export async function updateSlideJobAction(jobId, progress, currentStep): Promise<void>
export async function finishSlideJobAction(jobId, status: "completed"|"failed", error?): Promise<void>
```
- `start`: `container.processingJobs.create({ id: \`pj-slide-generation-${ts}-${rand}\`, type:"slide-generation", status:"running", progress:0, total, currentStep:"Generando diapositivas", courseId, materialId:null, error:null })`.
- `update`: `container.processingJobs.update(jobId, { progress, currentStep })`.
- `finish`: `update(jobId, { status, progress: status==="completed"?total:…, currentStep, error })`.

**2. Cableado en el cliente** (`slides-client.tsx`)
- Al iniciar un batch (`enqueueAll`): llamar `startSlideJobAction(courseId, ids.length)` → guardar `jobId`.
- En el callback de progreso de la cola (por slide completado): `updateSlideJobAction(jobId, done, \`Diapositiva ${done}/${total}\`)`.
- Al terminar: `finishSlideJobAction(jobId, summary.failed>0 ? "failed" : "completed", …)`.
- La generación individual también abre un job de `total:1`.

**3. UI Jobs**
- Sin cambios: `JobsPanelContent` y `findRecentWithCourseNames` son agnósticos al tipo (solo excluyen `pipeline-run`). La etiqueta "Generación de diapositivas" ya existe en `job-labels.ts`.

*Nota:* como el batch corre en el cliente y las actualizaciones son por-slide, el estado "running" será visible mientras dure. Se actualiza progreso por slide para que el panel (poll 1.5s) lo muestre en vivo.

## D6 — Exportación PPT con diálogo de guardado (R6)

### Causa raíz técnica
El comando Rust `save_file(path, data: String)` escribe `data` como texto UTF-8 (`std::fs::write(&path, data)`). Un PPTX es binario; pasarlo como string lo corrompe. Se necesita un comando que **decodifique base64 → bytes**. El crate `base64` ya se usa en `extract_pdf`.

### Cambios

**1. Nuevo comando Rust** (`src-tauri/src/lib.rs`)
```rust
#[tauri::command]
async fn save_file_base64(path: String, data: String) -> Result<(), String> {
    use base64::{engine::general_purpose::STANDARD as BASE64, Engine};
    let bytes = BASE64.decode(&data).map_err(|e| format!("Invalid base64: {}", e))?;
    std::fs::write(&path, bytes).map_err(|e| e.to_string())
}
```
- Registrar en `invoke_handler![extract_pdf, save_file, save_file_base64, open_file_dialog]`.

**2. Cliente — diálogo de guardado** (`app/courses/[id]/slides/slides-client.tsx` `handleExportPpt`)
- Detectar Tauri con el patrón `isTauri()` de `export-modal.tsx`.
- Rama Tauri:
  ```ts
  const { save } = await import("@tauri-apps/plugin-dialog");
  const { invoke } = await import("@tauri-apps/api/core");
  const path = await save({ filters:[{name:"PowerPoint",extensions:["pptx"]}], defaultPath: result.filename });
  if (path) { await invoke("save_file_base64", { path, data: result.pptx }); toast("PPT guardado"); }
  ```
- Rama web (else): mantener blob + anchor download, con toast "Descargado en tu carpeta de descargas".
- Manejo de `result.error` (sin diapositivas / sin HTML) con toast de error (R6.4).

**3. Capabilities** — `dialog:default` ya está permitido en `capabilities/default.json`. `save_file_base64` es un comando propio (no requiere permiso de plugin adicional).
