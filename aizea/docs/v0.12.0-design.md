## D-A1 — Feedback visual al "Bajar nivel" (RA1)

**Contexto:** `handleExpandDepth` solo hace `setGenerating(true)`, no pasa nada a `TreeViewer`, y no hay placeholders. La infraestructura de `pendingNodeIds` (pulse/dim) ya existe pero solo la usan las mutaciones.

**Diseño:**
- `tree-client.tsx`: al iniciar la expansión, calcular las hojas objetivo (seleccionadas, o las del nivel más profundo si no hay selección) y pasar esos IDs + un flag `expanding` a `TreeViewer` como nueva prop `expandingLeafIds: string[]`.
- `TreeViewer.tsx`: por cada `expandingLeafId`, inyectar en el grafo de ReactFlow un **nodo fantasma** hijo (tipo `ghost`) posicionado bajo la hoja, con estilo gris punteado ("Generando…"). Se añaden al `laidOutNodes` memo, no tocan BD.
- `TreeNode.tsx` (o un `GhostNode` nuevo): render de caja gris `border-dashed bg-muted/40 animate-pulse` con texto "Creando subnivel…".
- `TreeControls.tsx`: el botón "Bajar nivel" ya se deshabilita con `busy`; conectar `busy` también a `generating` durante expansión (RA1.2).
- Al llegar `result.nodes`, se limpian los fantasmas (se reemplaza el estado por el árbol real).

**Decisión:** nodo fantasma como tipo de nodo ReactFlow separado (composición), no reutilizar TreeNode con flags — evita ramificar la lógica de TreeNode.

## D-A2 — Auto-refresco y banner correcto tras generar árbol (RA2)

**Causa raíz (del análisis):** el banner late a rojo por el latch `hasFailed = job.hasFailed || job.isStuck`, y `isStuck` se activa tras 5 min sin cambio de `progress` (fases lentas legítimas). Además el color lo decide el "representante" del grupo, no un agregado all-completed/any-failed. El `router.refresh()` de completado SÍ funciona para el contenido del árbol.

**Diseño:**
- `usePipelineStore.ts`: subir `STUCK_THRESHOLD_MS` a un valor no-agresivo (p.ej. 15 min) **y** dejar de tratar `isStuck` como `hasFailed` en el banner (stuck ≠ failed). Stuck se muestra como aviso ("puede estar tardando"), no como error rojo.
- `GlobalPipelineBanner.tsx`: el color del grupo debe ser un **agregado real**: rojo solo si algún job del grupo está `failed`; verde si todos `completed`; azul si alguno running/pending. Implementar la semántica que el comentario ya documentaba pero no cumplía.
- Confirmar que al completarse el árbol el banner pasa a verde y el auto-refresh (ya presente) actualiza la vista (RA2.1/RA2.3).

## D-C3 — Generación de slides server-side (RC3) [DECISIÓN ORACLE: Opción A]

**Problema:** la generación corre en `SlideGenerationQueue` del cliente; al desmontar se cancela y el store se resetea → la generación PARA y los marcadores desaparecen. El `ProcessingJob` solo guarda progreso agregado, no estado por-slide.

**Diseño (worker server-side, espejo del pipeline del árbol):**
1. **Estado por-slide en BD:** usar `Slide.status` (String, ya existe) con vocabulario `PENDING → GENERATING_CONTENT → GENERATING_HTML → GENERATED / FAILED`. Es la fuente de verdad por-tarjeta, sobrevive navegación/recarga.
2. **Use-case compartido:** extraer la lógica de `generateSlideContent` y `regenerateHtmlDesign` a métodos de aplicación que tanto la server action como el worker invocan (sin que el worker llame a la action). Ya viven en `SlideGenerationService` → reutilizar directamente.
3. **Worker:** añadir un worker de tipo `slide-generation` (generalizar `PipelineWorker` por `type`, o segundo worker con primitivo `runSlideBatch(courseId, phases)`), concurrencia 3, try/catch por slide. Actualiza `Slide.status` y el `ProcessingJob` agregado (progress/total) tras cada slide. Chequea el `status` del job meta entre slides para cancelación cooperativa.
4. **Acciones:** `startSlideGenerationAction(courseId, phases)` (enqueue + pump fire-and-forget, espejo de `startPipelineAction`) y `getSlideStatusesAction(courseId)` → `{id,status}[]`.
5. **Cliente:** la vista de slides poll `getSlideStatusesAction` cada 1.5s mientras haya job `slide-generation` activo para el curso, y pinta `statusById` desde ahí. Eliminar `SlideGenerationQueue` + el reset en unmount. El store queda como proyección transitoria del poll.
6. **Recovery:** conectar el `recover()` del worker al bootstrap (`/api/health`) para reanudar batches interrumpidos (saltar `GENERATED`).
7. **Idempotencia:** un job `pending`/`running` de `slide-generation` para el curso = no-op (evita doble arranque).

**Riesgo/beneficio:** reutiliza ~80% del patrón probado del pipeline; la lógica LLM ya es server-side, se mueve orquestación no lógica. Elimina fragilidad browser-resident.

## D-D1 — Export PPT como Job (RD1)

**Diseño:** `exportAllSlidesPptAction` deja de ser síncrona-bloqueante en el sentido de invisibilidad: crea un `ProcessingJob` tipo `ppt-export` (start → progress por slide → finish) visible en Jobs. Como la generación del pptx es relativamente corta y necesita devolver bytes al cliente para el diálogo de guardado, el job se usa para **visibilidad** (running → completed) mientras la action construye el buffer; el buffer se devuelve al cliente al terminar. Etiqueta `ppt-export` en `job-labels.ts`.

## D-D3 — PPT nativo editable + notas (RD3) [DECISIÓN ORACLE: Opción A]

**Diseño (pptxgenjs nativo desde datos estructurados):**
1. **Query:** extender `exportAllSlidesPptAction` para incluir `boxes` de cada slide (patrón del PDF export: `include: { boxes: true }`), más `kind`.
2. **Servicio `PptExportService.generatePptx`:** reemplazar `addImage` full-bleed por template nativo:
   - Título (numericPath + title) como `addText` grande arriba.
   - Cuerpo: `script` (guion) como texto principal; `exercise1/2` como bullets si existen. `relevance` como callout opcional.
   - Fondo blanco, acento azul (coherente con el diseño de la app).
3. **Notas del orador:** `pptSlide.addNotes("GUIÓN\n<script>\n\nRELEVANCIA\n<relevance>\n\nNARRATIVA\n<narrative>\n\nEJERCICIOS\n1) <e1>\n2) <e2>")` — plain-text con etiquetas en mayúscula (usar `BOX_LABELS`). Es la única API posible (`addNotes` solo texto).
4. **Fórmulas:** v1 → emitir el TeX como texto (editable, sin renderizar). Escalado futuro: rasterizar solo fórmulas.
5. **Figuras (`kind === "figure"`):** mantienen `addImage` de su imagen real (split limpio: concepto = texto nativo, figura = imagen).
6. **Eliminar Playwright del path de PPT:** ya no se renderiza HTML→PNG para conceptos. `SlideImageRenderService` solo se mantiene si el PDF lo necesita.
7. Limpiar el duplicado muerto `lib/services/PptExportService.ts` + `exportSlidesPptAction` si nada más los usa.

**Pérdida asumida:** el layout visual bespoke del LLM no se reproduce pixel-perfect (imposible sin motor de layout, que solo da imagen). "HTML como referencia" se honra reflejando la anatomía de contenido. Explícito con el cliente.
